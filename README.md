# Сервис подачи заявок на услугу

Заявитель заполняет заявку, прикладывает документ, оплачивает и отправляет её на рассмотрение.
Оператор рассматривает заявку и принимает решение: одобрить, отклонить или вернуть на доработку.

**Стек:** Python 3.12, FastAPI, SQLAlchemy 2 (async), PostgreSQL 16, Alembic · React 19, TypeScript,
Redux Toolkit + RTK Query, Mantine · Docker Compose · pytest, Playwright.

---

## Запуск

```bash
docker compose up
```

| Что | Адрес |
|---|---|
| Приложение | http://localhost:3000 |
| API и Swagger | http://localhost:8000/api/docs |
| PostgreSQL (для просмотра клиентом БД) | `localhost:5433`, база `applications`, `app` / `app_local_password` |

Создавать `.env` не нужно: compose читает настройки из `.env.example` (в нём только безопасные
значения для локального запуска), а поверх — из `.env`, если он есть. Свои значения кладите в `.env`,
он в `.gitignore`. При старте backend сам применяет миграции и создаёт демо-пользователей.

### Пользователи

Пользователи создаются автоматически при каждом старте backend (`backend/scripts/seed.py`,
повторный запуск ничего не меняет), поэтому после `docker compose up` они есть в любой новой базе.
Пароль — логин с окончанием `pass`.

| Кабинет | Логин | Пароль |
|---|---|---|
| Заявитель | `applicant1` | `applicant1pass` |
| Заявитель | `applicant2` | `applicant2pass` |
| Заявитель | `applicant3` | `applicant3pass` |
| Оператор | `operator1` | `operator1pass` |
| Оператор | `operator2` | `operator2pass` |

Двух заявителей достаточно, чтобы проверить, что один не видит заявки и файлы другого.

### Тесты

Unit- и интеграционные тесты backend (API + настоящий PostgreSQL в отдельной базе
`applications_test`, рабочие данные не затрагиваются):

```bash
docker compose run --rm backend pytest
```

Frontend проверяется линтером и сборкой: `cd frontend && npm ci && npm run lint && npm run build`.
Те же проверки backend и frontend запускаются в GitHub Actions (`.github/workflows/ci.yml`)
на каждый push и pull request.

### Сквозной тест в браузере (необязательно)

Сквозной сценарий на Playwright проходит весь путь заявки через интерфейс: создание, документ,
оплата, отправка, возврат оператором на доработку, повторная отправка без оплаты, одобрение.
ТЗ его не требует, поэтому он **не входит в `docker compose up`** и запускается отдельно.
В GitHub Actions он идёт отдельной задачей при push в `main` и по ручному запуску (Actions →
CI → Run workflow); при ошибке к запуску прикладываются отчёт Playwright и скриншоты.

Вариант 1 — в контейнере. Первая сборка скачивает образ с Chromium (~1,9 ГБ), поэтому занимает
время; сам тест идёт около 30 секунд:

```bash
docker compose -f docker-compose.yml -f docker-compose.e2e.yml run --rm --build e2e
# вернуть обычные настройки (тест переключает шлюз оплаты на стабильный)
docker compose up -d --build
```

Вариант 2 — без скачивания браузера, в установленном Google Chrome (нужен Node.js):

```bash
docker compose -f docker-compose.yml -f docker-compose.e2e.yml up -d --build backend frontend
cd e2e && npm ci
E2E_BASE_URL=http://host.docker.internal:3000 PW_CHANNEL=chrome npx playwright test
cd .. && docker compose up -d --build
```

## Что сделано

**Заявитель**
- Черновик: ФИО, телефон, тип услуги (справочник из 5 услуг с ценами в TJS), комментарий.
  Черновик можно править и удалить.
- Один документ PDF, JPG или PNG до 5 МБ; повторная загрузка заменяет файл.
- Оплата через заглушку шлюза, которая иногда отвечает с задержкой, а иногда ошибкой.
  Повторный запрос (двойной клик, повтор после таймаута) не списывает деньги второй раз.
- Отправка на рассмотрение — только с документом и после оплаты.
- Список своих заявок со статусами, фильтром и пагинацией; карточка с историей.
- После возврата на доработку — правка и повторная отправка без новой оплаты.

**Оператор**
- Очередь отправленных заявок с фильтрами по статусу и услуге, постранично.
- Карточка заявки, просмотр и скачивание документа.
- Решения: одобрить, отклонить, вернуть на доработку; при отклонении и возврате комментарий
  обязателен. При отклонении оплата возвращается заявителю.

**Общее**
- Вход по логину и паролю: JWT access-токен + refresh-токен в httpOnly cookie с ротацией.
- Роли заявителя и оператора; заявитель видит только свои заявки — это проверяется на сервере.
- История: по каждой заявке видно, кто, когда и с каким комментарием менял статус.
- Единый формат ошибок API с сообщениями на русском.
- Тесты: 108 unit, 43 интеграционных; дополнительно — необязательный сквозной сценарий в браузере.

## Что не сделано и известные ограничения

- **Зависший платёж.** Если сервер упадёт ровно между списанием и записью результата, платёж
  останется в статусе `processing`, и заявку нельзя будет изменить. Нужна фоновая сверка со
  шлюзом по ключу платежа — не сделано.
- **Возврат денег** выполняется синхронно в одной транзакции с решением оператора: не удался
  возврат — не сохранится и решение. С настоящим шлюзом лучше outbox и повторные попытки.
- **Файлы не проверяются антивирусом**; проверяется только тип по сигнатуре и размер.
- Нет ограничения частоты попыток входа (rate limiting) и блокировки после неудачных попыток.
- Нет назначения заявки конкретному оператору: двое могут открыть одну заявку, но решение примет
  только первый — второй получит понятную ошибку 409.
- Frontend покрыт сквозным тестом, отдельных unit-тестов компонентов нет: по ТЗ тесты нужны на
  переходы статусов и оплату, они написаны на backend.
- Деплой не делался: целевой сценарий — локальный запуск через `docker compose up`.

## Решения и почему

### Статусы

```
draft ──оплата──► paid ──отправка──► submitted ──одобрение──► approved
                                       │   ▲    └──отклонение──► rejected (деньги возвращаются)
                            возврат    │   │ повторная отправка
                       (с комментарием)▼   │ (без новой оплаты)
                                      returned
```

| Статус | Значение | Кто переводит дальше |
|---|---|---|
| `draft` | черновик: можно править, менять документ, удалить | заявитель оплачивает |
| `paid` | оплачен, ещё не отправлен | заявитель отправляет |
| `submitted` | на рассмотрении у оператора | оператор: одобрить / отклонить / вернуть |
| `returned` | возвращён на доработку с комментарием | заявитель правит и отправляет снова |
| `approved` | одобрен — финальный | — |
| `rejected` | отклонён, оплата возвращена — финальный | — |

- **Оплата — отдельный статус**, потому что это отдельный шаг, видимый заявителю («оплачено, но
  не отправлено»). При этом сам платёж — отдельная сущность со своим статусом
  (`processing / succeeded / failed / refunded`): проверка «без оплаты отправить нельзя» смотрит на
  успешный платёж, поэтому после возврата заявка уходит повторно без новой оплаты.
- **Документ прикладывается до оплаты:** после оплаты черновик фиксируется, иначе можно было бы
  оплатить и остаться без возможности приложить файл.
- **Править** можно в `draft` и `returned`; **удалить** — только неоплаченный `draft` (мягкое
  удаление, история попыток оплаты сохраняется). После оплаты нельзя сменить услугу — от неё
  зависела списанная сумма.
- **Отклонение — финал** с возвратом денег: услуга не оказана. Подать заново — новой заявкой.
- **Оператор не видит черновики и оплаченные, но не отправленные заявки** — для него их нет (404).

**Где проверяется.** Все переходы описаны одной таблицей в `backend/app/domain/status_machine.py`:
откуда, каким действием, куда, какой ролью, нужен ли комментарий. Статус меняется только в
`ApplicationWorkflow.apply()`: под блокировкой строки (`SELECT … FOR UPDATE`) проверяются условия
ТЗ (есть документ, есть оплата), затем переход по таблице, и в той же транзакции пишется запись в
историю. Недопустимый переход → 409, чужая роль → 403, нет комментария → 422. Статусы в БД —
enum-тип PostgreSQL. Фронтенд не дублирует правила: сервер возвращает с заявкой список
`allowed_actions`, и интерфейс показывает только эти кнопки.

### Оплата: почему не будет второго списания

Слои защиты, от фронтенда до базы:

1. **Фронтенд** создаёт на попытку оплаты один `Idempotency-Key` и блокирует кнопку. Если ответ не
   пришёл за 7 секунд или пришёл `202` («ещё обрабатывается»), запрос повторяется с **тем же**
   ключом, пока не придёт итог. Новый ключ — только после окончательного отказа.
2. **Запрос с уже известным ключом** возвращает тот же платёж; шлюз второй раз не вызывается.
3. **Строка заявки блокируется** на время проверки: одновременные запросы идут по очереди. Если у
   заявки уже есть успешный платёж, он и возвращается; если платёж ещё в обработке — `409
   PAYMENT_IN_PROGRESS`.
4. **В БД частичный уникальный индекс**: у заявки не может быть больше одного «живого» платежа
   (`processing / succeeded / refunded`), даже если в коде окажется ошибка.

Шлюз вызывается вне транзакции (может отвечать секундами) и под `asyncio.shield` в своей сессии БД:
если клиент оборвал соединение по таймауту, оплата всё равно завершится и запишется, а повтор с тем
же ключом получит готовый результат. Пока платёж в обработке, заявку нельзя менять.

**Заглушки шлюза — две** (`PAYMENT_GATEWAY` в `.env`): `flaky` по умолчанию — случайная задержка,
иногда очень долгая (дольше, чем ждёт фронтенд), и ~20% отказов; `stable` — всегда успешно, для
демонстрации и сквозного теста. Все вероятности настраиваются.

Тесты на это — `backend/tests/integration/test_payments.py`: двойной клик при медленном шлюзе,
обрыв запроса клиентом и повтор, отказ шлюза и повторная попытка, отказ БД сохранить второй платёж.

### Хранение файлов

- Локальный диск в Docker-томе за интерфейсом `FileStorage` (`save / read / exists / delete`).
  Облачное хранилище (S3, MinIO, Vercel Blob) подключается новой реализацией без изменений в
  сервисах. MinIO не стал добавлять: лишний контейнер и настройка бакета усложняют
  `docker compose up`, а суть — в проверках, а не в хранилище.
- **Тип проверяется по содержимому** (сигнатура в первых байтах) и должен совпадать с
  расширением: переименованный `.exe` не пройдёт. Размер считается при чтении, лишний байт сверх
  5 МБ обрывает загрузку. Заведомо огромные запросы отсекаются ещё до разбора тела.
- Файлы лежат под случайными ключами, вне любой публичной папки, раздаются только через API.
- **Чужой файл не скачать:** владелец проверяется в самом SQL-запросе, чужая заявка или файл
  возвращают 404 (а не 403 — не раскрываем, что такая заявка существует). Подобрать ссылку
  бесполезно. Ответ — с `Content-Disposition: attachment`, `nosniff`, без кеширования.

### Вход и роли

- Access-токен (15 минут) хранится только в памяти фронтенда; refresh-токен (7 дней) — в httpOnly
  cookie, которую JavaScript не видит. При каждом обновлении выдаётся новый refresh-токен;
  повторное использование старого закрывает все сессии пользователя.
- Роль берётся из БД. Переключатель «Заявитель / Оператор» на странице входа лишь выбирает кабинет —
  войти в чужой кабинет сервер не даст.
- Все маршруты, кроме входа, обновления токена и health-check, закрыты по умолчанию: проверка
  токена висит на роутере, поэтому новый эндпоинт не может случайно оказаться публичным.
- Фронтенд и backend — разные приложения на разных портах, поэтому CORS разрешён явно для адресов
  из `CORS_ORIGINS`.

### Устройство кода

**Backend** — слои: `routers` (только HTTP) → `services` (бизнес-логика, транзакции) →
`repositories` (запросы к БД). Рядом: `domain` (статусы и правила документа без зависимостей от БД и
HTTP), `integrations` (заглушки шлюза), `storage` (файлы), `models` (таблицы), `schemas` (Pydantic).

**Frontend** — Redux Toolkit + RTK Query. Справочник услуг загружается сразу после входа и живёт в
store всю сессию. Все запросы идут через один axios-клиент, который при истёкшем токене один раз
обновляет его и повторяет запрос. Правила валидации полей повторяют серверные (zod).

## Что сделал бы иначе, будь больше времени

- Фоновая сверка зависших платежей со шлюзом и outbox для возвратов с повторными попытками.
- S3-совместимое хранилище с подписанными ссылками и антивирусная проверка загрузок.
- Статус «взята в работу» с назначением оператора и уведомления заявителю (email/SMS) о решении.
- Rate limiting входа и журнал действий операторов.
- Генерация TypeScript-типов из OpenAPI вместо ручных, unit-тесты фронтенда (Vitest).
